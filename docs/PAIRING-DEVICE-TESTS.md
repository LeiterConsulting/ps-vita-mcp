A late confirmation was rejected with HTTP 409 and created no credential. Individual credential confirmation and wider physical/lifecycle qualification remain open. Before testing, the operator must be physically present, retain the old packages/configuration and private credential, stop active desktop input/work sessions, verify neutral leases, and complete a normal reboot. Install and activate the candidate manually once. Do not boot-load Control, hot unload helpers, start a second pair in one boot, or discard an uncertain session guard. Use the candidate desktop bridge with the old private configuration and exact new build pins. The Companion allowlist requires separately reviewed new identities.

## Repaired failures and next test

Starter 01.05 failed to show the code after physical approval. The actual UI worker host harness reproduced a race where a stale poll could overwrite a code-generation error. Starter 01.06 invalidates that reply, latches errors, records bounded diagnostic return codes, and formats the six-digit code without relying on padded SDK formatting. The regression harness fails when the revision invalidation is removed; all nine repaired UI groups pass. Hardware code display then passed. The earlier SDK failure cause remains unconfirmed until its diagnostic evidence is collected.

The first 01.06 confirmation arrived after the original deadline. It was rejected cleanly, so it does not establish credential persistence or inspection permissions. The next test uses a private loopback PC form to submit the physically displayed code immediately, save the individual credential privately, and check status/session access and five denied write routes. The form passed four state tests and six local HTTP boundary checks. Those checks sent no Vita request and are not hardware acceptance. No code or credential is copied into these public records.

Workbench candidate staging also had a host defect: its journal supplied an attempt ID to an upload function that accepted only two arguments. The bridge now accepts a validated optional ID. Actual MCP tests against a simulated HTTP device verify that journal, upload and both readbacks use that ID. A lost reply retains the ID and is recovered by reads without a second POST. The old signature fails the new regression. Native candidate staging through this repaired path remains to be tested separately.

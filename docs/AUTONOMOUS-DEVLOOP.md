## Control-free foreground iteration

Open the installed, paired DevLoop 01.04 and leave it healthy and paused. `vita_workbench_prepare_script_session(expected_devloop_build)` observes it twice without Control, requiring the exact native build and stable advancing runtime/scene identity. Its successful response supplies `runtime_identity.pid`, `runtime_identity.run` and `expected_revision` for `vita_workbench_script_session`. This readiness means script work only; it does not prove displayed foreground PID, capture mapping or input delivery.

A script session accepts 1–8 named Lua candidates, each with inline source, exact UTF-8 SHA-256 and finite metric predicates. Sources are at most 16 KiB; each measurement polling window is 0.25–30 seconds with 0–3 seconds warmup, and their planned aggregate is at most 120 seconds, excluding request/restore time. HTTP delays can extend actual execution; cumulative metrics need appropriate normalization before ranking. Optional metric selection ranks accepted candidates by minimum or maximum; otherwise the first accepted candidate wins. The runner restores the original paused VM between runs and finishes there by default. Explicit `retain_best: true` reloads the winner into a fresh paused VM; its metrics belong to the earlier measured run. Native fallback retains the last Lua VM inactive, and older rollback history cannot be preserved.

The job freezes its endpoint and runtime pins, journals mutation intent and holds the shared local operation lock. Revision/hash checks detect ownership changes but do not create a remote scene lease or eliminate another remote client's request race. Lost mutation replies are inspected without replay and stop further iteration/cleanup when ownership is uncertain. Sleep, network loss, endpoint drift or a new process stops the job. Without qualified Control there is no work/input lease, power tick, keep-awake, brightness control, capture or synthetic input.

The CLI exposes `prepare-script <DevLoop-native-build-ID>` and `script-session <MANIFEST> <SHA256>`. Use fresh preparation pins in the UTF-8 JSON manifest; its command-line hash covers exact file bytes, while each candidate hash covers its inline source. `tools/prove_script_session.py <DevLoop-native-build-ID>` is an explicit live demonstration through stdio MCP: prepare, run two measured movement scenes, rank and restore. It accepts optional `--retain-best`. [Workbench](../workbench/README.md#control-free-script-sessions) documents fields, limits, journals and examples.

These PC paths have actual HTTP/MCP host fixtures. The October 12 live two-candidate proof initially failed its cumulative-distance ranking assertion: differing HTTP delays produced unequal execution times, despite successful runs and restoration. The corrected fresh proof passed through stdio MCP on the installed Vita, observing rates 60 and 120, selecting the faster candidate and restoring the original inactive-Lua/native scene paused with unchanged native world and exact build/PID/run identity. A separate `retain_best` proof left the selected exact source in a fresh paused VM with zero updates; guarded cleanup subsequently restored the original VM and native world/parameters/score/mode. One PC cleanup-journal write failed after confirmed rollback: read-only reconciliation established the current revision without rollback replay, before a separately journaled native-restoration action. The initial ranking failure and cleanup event are retained.

This is hardware proof of the bounded metric-script loop and explicit retention, not launch, installation, input, power, sleep/reopen or complete autonomous operation. No Starter, Control, synthetic input, native-file or boot-configuration changes were used. A separate foreground screenshot confirmed the retained scene visually; capture is outside the session tools, and physical controls were not qualified. ## Control-backed preparation and target identity

Call `vita_workbench_doctor` to inspect services, then `vita_workbench_prepare_devloop` with the exact installed Control build ID and selected DevLoop version. Preparation refuses an existing input/work lease, pins both endpoints including the effective Control port, and requires healthy paused DevLoop. It can submit `CHRS00003` launch once when the runtime is transport-unavailable. It journals the intent first and inspects an uncertain result without repeating the launch. Authentication, protocol, version and configuration failures do not authorize a launch.

Preparation observes advancing runtime frames, stable revision/source ownership, progressing captures and a stable captured PID. Readiness has two separate meanings:

| Report field | Meaning |
| --- | --- |
| `ready_for_script_reload` | Healthy paused Lua runtime is available for script-only work; captured foreground identity can remain unverified. |
| `ready_for_input_trial` | Native DevLoop 01.04 reports `title_id: CHRS00003` and a positive integer PID matching both captured foreground observations; its stable native build matches the caller's exact expected build pin. |
| `ready_for_lua_trial` | Compatibility field with the same strict input readiness requirement. |
| `result: runtime_ready_target_unverified` | Runtime inspection/script work is available; synthetic input is blocked. |
| `result: runtime_ready_build_unpinned` | The 01.04 target is mapped, but no expected native build pin was supplied. Script work is available; synthetic input is blocked. |

The 01.04 native source publishes `title_id`, `pid`, `run` and `build_id` in successful status, script, input and log responses. `run` is a per-process correlation value, not a credential; `build_id` fingerprints the declared native source and pinned build inputs. Preparation and trials retain the full runtime identity, stop after a process/build change, and refuse restoration into a different runtime. Input readiness/trials require `expected_devloop_build` to pin the reviewed candidate; the CLI spelling is `--devloop-build`. It is optional only for script-only 01.04 work. Read the pin from the actual build report's `nativeIdentity.buildId` or `package.buildId`. Reports distinguish `native_candidate_pin_verified` from `captured_target_mapped`.

Legacy 01.02 and 01.03 do not publish this mapping. A stable display PID alone could belong to LiveArea or another application. Consequently those legacy runtimes cannot run input-bearing Workbench profiles. Script-only profiles with no input steps remain available when explicitly selecting the legacy version. DevLoop 01.04 passed its pinned-SDK native build, installation, stable native identity and 55-step physical-device Lua reload/recovery proof, including original native scene restoration paused. The operator also confirmed normal START+SELECT exit. Control capture-to-PID mapping, synthetic input and sleep/reopen remain open. These observations predate the boot recovery above. [Candidate identities and evidence](autonomous-candidate-validation.json).

`vita_workbench_run_trial` rechecks native target identity before loading an input-bearing profile and before each synthetic step. Trials freeze their own endpoints, retain profile/source/Control pins, journal mutations and restore an owned scene paused. The PC lock prevents competing local jobs; it is not a general multi-host ownership protocol. Human input and physical sensor acceptance remain independent.

For the CLI, `prepare <Control-build-ID> --version 01.04 --devloop-build <DevLoop-build-ID> --timeout 30` succeeds only with input readiness. Version 01.04 is the default. Add `--script-only` to accept script readiness without target mapping; for an installed legacy runtime also select `--version 01.02` or `--version 01.03` and omit the unsupported native build pin. Polling uses the selected 2–60-second deadline plus in-flight socket timeouts. [Workbench details](../workbench/README.md).

```powershell

```

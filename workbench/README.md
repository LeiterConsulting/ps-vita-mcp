# Vita Workbench

Workbench supplies Control-free Lua iteration, native lifecycle qualification, runtime preparation, candidate staging, input qualification, screen evidence, metrics, managed-file recovery and paused restoration. It adds sixteen tools to the Resident MCP (36 total: seven Resident, thirteen Control and sixteen Workbench). The new [native lifecycle candidate](../docs/NATIVE-LIFECYCLE.md) adds preview, journaled install/launch/evaluate/exit cycles and read-only reconciliation for a dedicated owned lab title. The accepted DevLoop installation still uses the manual path until that adapter is extended and qualified.

For script iteration, open the installed, paired DevLoop 01.04 once and leave it healthy and paused; Control and Starter are not required. Start with `vita_workbench_prepare_script_session`. For Control-backed screen/input/file jobs, use `vita_workbench_doctor` and load Starter's matched pair once after a confirmed normal boot. Boot Resident can stage candidates even if runtime Control is absent. The older trial path supports paused DevLoop 01.02, 01.03 and 01.04; legacy versions are script-only. Native input qualification requires Input Target (`CHRS00012`).

## Control-free script sessions

`vita_workbench_prepare_script_session(expected_devloop_build)` makes two read-only observations of already open DevLoop 01.04. It requires an exact lowercase native build ID, healthy paused state, advancing frames and stable native identity and scene. On `ready_for_script_reload: true`, use `runtime_identity.pid`, `runtime_identity.run` and `expected_revision` as the next session's pins. Read the build ID from the report matching the installed app: `dist/devloop/build-report.json`, field `nativeIdentity.buildId` or `package.buildId`. This is self-reported runtime identity, without Control capture-to-PID or foreground input qualification.

`vita_workbench_script_session` takes those pins, `expected_devloop_build` and 1–8 candidate objects. Each contains `name`, inline `source`, its exact UTF-8 `source_sha256`, and 1–8 `checks`; optional `duration_s` and `warmup_s` default to 1 and 0.25 seconds. Names are unique 1–32 ASCII letters/digits/underscores/hyphens. Sources are 1–16,384 bytes. Measurement polling windows are 0.25–30 seconds per candidate, warmup 0–3 seconds, and their planned aggregate is at most 120 seconds, excluding requests and restoration. HTTP delays can extend actual execution and wall time; this is not an exact simulation-duration or performance benchmark.

Each check names a numeric `metric` and at least one of `min`, `max` or `equals`. Metrics and predicate values must be finite; a missing metric fails its check. Optional `selection: {"metric": "rate", "direction": "max"}` ranks accepted candidates (`min` is also supported). Without selection, the first accepted candidate wins; ties keep the earliest. Cumulative metrics can be biased by unequal execution time; use appropriate normalization in the script, as the demo does with distance divided by observed simulation elapsed time. This evaluates declared measurements, not visual quality or physical input.

The runner pins the endpoint and complete native build/PID/run identity, journals intent before writes and holds the shared local operation lock for the whole job. It restores the original paused VM between candidates, including its retained state. By default it also finishes on that original scene. Explicit `retain_best: true` instead reloads the selected source into a **fresh VM, paused**; measured metrics describe its earlier run, not the fresh retained VM. Native fallback keeps the last Lua VM inactive, and the single rollback slot cannot preserve an older rollback history.

An uncertain mutation is inspected through read-only requests and is never replayed. Uncertain ownership, process restart, endpoint drift or another editor's scene change stops further iteration and can leave restoration skipped/unconfirmed. Inspect the report before another job. The local lock is not a remote scene lease: revision/hash guards cannot eliminate another remote client's check/request race. These tools do not launch or install apps, capture screens, inject input, acquire an input/work lease, tick power or keep the Vita awake. Sleep or network loss can interrupt them.

For an explicit live two-candidate demonstration through a fresh stdio MCP:

```powershell
$devloop = Get-Content .\dist\devloop\build-report.json -Raw | ConvertFrom-Json
.\.venv-devloop\Scripts\python.exe tools\prove_script_session.py $devloop.nativeIdentity.buildId
```

The helper prepares fresh pins, generates and hashes two moving-circle scenes, checks movement metrics, ranks distance per observed simulation second and restores the original scene. Add `--retain-best` only when you want the selected source left fresh and paused. Its manifest and preparation/result files stay under `.devloop-private/script-session-proofs/`; session journals are under `evidence/workbench/script-session-*` and can be read with `vita_workbench_read_report`.

For your own plan, the CLI equivalents are:

```powershell
.\.venv-devloop\Scripts\python.exe -m workbench.cli prepare-script <DevLoop-native-build-ID>
$manifestHash = (Get-FileHash .\outgoing\script-session.json -Algorithm SHA256).Hash.ToLowerInvariant()
.\.venv-devloop\Scripts\python.exe -m workbench.cli script-session .\outgoing\script-session.json $manifestHash
```

Create the UTF-8 JSON manifest after successful preparation, using its fresh pins. Its fields are `candidates`, `expected_devloop_build`, `expected_pid`, `expected_run`, `expected_revision`, optional `retain_best` and optional `selection`. Candidate sources are inline text; hash the exact UTF-8 encoding of that text, including its line endings. The separate command-line SHA-256 covers the manifest's exact file bytes; the CLI rejects files over 150 KiB. `prepare-script` succeeds only for script readiness and `script-session` only for `result: passed`. A stale revision or process pin blocks the job rather than adopting a new scene.

Preparation defaults to `allow_launch: false`. Its optional launch path requires explicit intent and exact Resident broker build/instance pins. The [legacy broker core/client](../resident/launch_broker/README.md) is retained in Resident 0.1.5 with native submission disabled; Resident 0.1.2 has no broker protocol. A closed DevLoop therefore requires manual opening on the current installed system. The separate [native lifecycle candidate](../docs/NATIVE-LIFECYCLE.md) targets the dedicated `VMCP00001` lab first. The corrected 0.1.5 is now boot-loaded and exact-binary verified with a fresh unblocked, installer-ready native instance and Promoter unloaded. Four fixed-Lab install/launch/evaluate/graceful-exit cycles across two native builds passed on hardware; same-build journal durability after reboot remains pending; the original unknown promotion receipt is retained without replay. [Current incident](../docs/NATIVE-LIFECYCLE.md#october-12-native-promotion-incident). Lost replies are inspected under their original attempt, never resubmitted.

## Control-backed preparation and target identity

`vita_workbench_prepare_devloop` removes the manual app-launch step when matched Control is already available. Supply `expected_control_build` from the installed build's report, select `expected_devloop_version` (`01.04` by default, or explicitly select historical `01.02`/`01.03`), and optionally set `timeout_s` to 2–60 seconds. Supply `expected_devloop_build` from the exact candidate's `dist/devloop/build-report.json` (`nativeIdentity.buildId` or `package.buildId`) for input readiness. Polling respects that deadline; an in-flight network request retains its separate socket timeout.

The tool requires matching DevLoop/Control host configuration, freezes the foreground settings and effective Control host/port/token for the operation, and refuses an existing input or work lease. Configuration or port-override drift stops further work; cleanup continues to use the original endpoint. It accepts an already healthy paused DevLoop without launching again. Only a transport-unavailable DevLoop endpoint permits one journaled `CHRS00003` launch. Authentication, configuration, version and protocol errors block preparation. Running or faulted scenes remain untouched.

A native launch receipt is followed by two runtime observations: healthy paused state, advancing DevLoop frames, stable revision/source hash, advancing captures and a stable positive display PID. A lost launch reply is reconciled through inspection without repeating launch; a rejected or invalid receipt stays blocked even if a healthy runtime becomes visible. LiveArea confirmation dialogs time out with evidence; the tool never sends a blind tap or simulated control. It saves launch/runtime images and its journal under `evidence/workbench/prepare-devloop-*`, maintains a journaled temporary work-power lease, and ends that lease in cleanup. No scripts, input, packages, modules or boot configuration are changed.

**Native identity:** 01.04 reports `title_id`, native positive `pid`, a 32-hex per-launch `run`, and a 64-hex source `build_id` in status, script, input and logs. The run value correlates clocks/PID; it is not secret or authentication. CMake regenerates the build fingerprint from canonical native/compiler inputs, local headers, Lua sources, generator and toolchain lock. Package verification independently checks that manifest, ELF identity, repeat ELF-to-SELF conversion and exact VPK executable bytes. During preparation/trials, the PC pins and rechecks the entire native identity tuple across observations and mutation receipts.

Legacy 01.02/.03 has no verifiable native process mapping and reports `runtime_ready_target_unverified`, `ready_for_script_reload: true`, and both input/Lua-trial readiness flags false. A mapped 01.04 runtime without the caller's build pin reports `runtime_ready_build_unpinned` and remains script-only. Input readiness requires the exact caller build pin and native `CHRS00003` PID matching both captured foreground observations. Doctor reports script readiness separately and never treats its uncaptured status check as input readiness. Host fixtures and package verification do not qualify installation, native launch behavior, dialogs or foreground identity on hardware.

## Control-backed trial workflow

1. Edit a project under `workbench/projects`, update the source/profile SHA-256 hashes and pin the Control build from its build report. Smoke and input profiles provide examples.
2. Call `vita_workbench_prepare_devloop` if DevLoop is not already open and paused. Script-only profiles can proceed when `ready_for_script_reload` is true. Profiles with synthetic input need `ready_for_input_trial`; the trial independently requires the exact `expected_devloop_build`, native title/PID matching before loading a script and before each input, and stable run/build throughout. Call `vita_workbench_run_trial` with relative profile, profile hash, Control build and native candidate build pin. Limits are 16 KiB source, 60 seconds, 20 steps and five seconds total input leases.
3. Inspect metrics, images, expiry and restoration. Requests are not replayed after uncertain replies. Changed ownership/revision prevents restoration over someone else's experiment.
4. Read `evidence/workbench/.../report.json` using `vita_workbench_read_report`. Mutation intent is journaled before requests. Power heartbeats have a separate journal.

Native physics, ball, added obstacles and score are preserved; the previous mode is restored paused. An originally unloaded VM can remain loaded but inactive after native restoration. Failed restoration fails the trial. A cross-process lock prevents competing bridges during a job, and each trial freezes its own endpoint settings for requests, power heartbeats and cleanup. Synthetic input checks native title/PID against a fresh capture before delivery; a legacy runtime can run profiles without input steps.

`workbench/prove_device.py` runs separate `input`, `files`, `trials` and `soak` gates through a fresh stdio MCP, pinning current native build reports. A failed button mask remains a failure while the independent focus result is retained. Shoulder buttons are checked separately and in a combined mask. `watch_activity.py` supplies a bounded physical observation; its long window accommodates manual response time while each device work lease stays at 30 seconds. Creating `stop.requested` inside that observation's evidence directory ends it with cleanup.

Soak, Input Target qualification and managed-file verification freeze effective Control settings before their first baseline request. Qualification also pins the separate Target host, token and port before that baseline. Subsequent reads, work heartbeats and cleanup use those endpoints if configuration changes. The Lua proof helper guards its receipt-owned script revision/hash before later mutations and restoration; uncertain replies or another editor's scene leave cleanup skipped or unconfirmed. The older `bridge/prove_device.py` is a historical version-only proof helper; use the Workbench proof entry point for the current candidate.

Focus qualification polls read-only status while app exit completes, before any explicit release. A fresh kernel FOCUS cause and changed displayed PID are required; expiry and manual cleanup cannot count as focus proof. Physical observers keep their latest 128 samples in the readable report and all samples in `samples.jsonl`.

`watch_controls.py` observes five human gestures in paused native DevLoop: D-pad LEFT, each stick, front touch along the bottom edge and rear touch. Keep the Vita flat, wait for a separate dim cycle before each gesture, and hold it for eight seconds to accommodate network delays. This observer distinguishes sticks and panels through foreground telemetry, excludes motion or mixed input, and requires neutral release. It retains 64 recent samples plus the complete log; `--start-at` permits a fresh repeat from a particular gesture without erasing earlier evidence. Short gestures can fall between separate HTTP snapshots; a neutral sample at onset waits for a paired read instead of declaring a failure. Human visual confirmation remains separate.

`watch_disconnect.py sleep` or `wifi` renews bounded work until the first failed read, then stops heartbeats and only probes read-only recovery. A Wi-Fi pass requires reconnection before the last accepted lease expires, restored brightness, cleared work/dimming and unchanged inactivity progression. Leave the Vita still and disconnect its network externally for that independent gate. Changing Wi-Fi in Settings or carrying it out of range introduces physical activity. Manual sleep/wake uses the power button; the observer cannot force-wake it or reload native modules.

After an uncertain upload or copy, call `vita_workbench_verify_file` with its attempt, name, exact byte count, SHA-256 and Control build. The tool checks native hashes before and after two complete reads, retains `verified.bin` on the PC, and does not rewrite the device file. Its 30-second socket timeout accommodates bulk reads; verification failure is retained without replay. Keep the original mutation failure as separate evidence. `prove_synthetic_idle.py` checks that emulated controls leave idle dimming intact while work continues.

`vita_workbench_soak` checks status/capture for 10..3600 seconds with temporary work leases. It checks build, uptime, sequence and absence of synthetic input, and records latency. Wi-Fi and capture load affect device results.

## Power and native workflow

Control-backed screen/input/file/app work renews a temporary 30-second keep-awake lease. Every WorkKeeper job freezes its Control endpoint before the first lease and retains it for heartbeat/cleanup, including jobs outside preparation/trials. Those jobs renew while active and end it in cleanup. The Control-free script preparation/session tools use no lease or power tick and cannot keep the screen awake. Default Control dimming starts after 30 seconds without device activity, including motion, and uses 20% of observed brightness. Input, end/expiry or Wi-Fi loss restores brightness. Saved settings remain untouched. Power status reports brightness and motion freshness; work lease supports an external bounded job. Status reads alone do not renew.

Build with `Build-Control.ps1` and `Build-Workbench.ps1`. `vita_workbench_stage_candidate` accepts the exact current Starter or Target package, checks source/package/accepted-artifact hashes, journals one boot-Resident upload and verifies two readbacks. It does not activate packages.

`vita_workbench_qualify_input` checks normal buttons, both additive sticks, both panels, neutral after expiry and kernel focus cancellation after Target self-exit. Pin both builds. Software input delivery is separate from physical controls, motion, brightness and sleep/wake acceptance.

The CLI is `.venv-devloop/Scripts/python.exe -m workbench.cli`; use `--help`. Control-backed runtime preparation is also available as `prepare <Control-build-ID> --version 01.04 --devloop-build <native-build-ID> --timeout 30`; `trial` accepts the same `--devloop-build` flag. That preparation returns exit code 1 for a blocked, target-unverified or build-unpinned result; add `--script-only` to explicitly permit success for a healthy script runtime without input readiness. Unlike `prepare`, the new `prepare-script` takes the DevLoop build as its positional pin. Restart the PC Resident MCP after bridge updates to expose all sixteen Workbench tools. Never restart Starter twice per boot or edit boot config for this candidate.
